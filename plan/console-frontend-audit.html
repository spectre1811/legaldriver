03

Design system audit

Token health, consistency gaps, dark mode readiness, and migration debt.
3.1

Token architecture — what's excellent

The tokens.css → tailwind.config.ts → globals.css pipeline is well-architected:

  • Single source of truth: all color values are CSS custom properties (no hex in Tailwind config)
  • Named for intent, not value: --ec-honey, not --yellow-500. Good.
  • 4px spacing grid: --s1 through --s24, consistent
  • 3-class elevation system: --e1 (cards), --e2 (dropdowns), --e3 (deep modal)
  • Three font stacks: Work Sans (UI), Fraunces (display), IBM Plex Mono (data)
  • Pre-mapped Tailwind classes: text-ec-ink, bg-ec-bronze-tint, shadow-ec-2
3.2

Token gaps — what's missing

GAP 1 — No text-warning / text-success tokens
Missing
The palette defines --success (#2e6b45) and --warn (#8c3b24) but only bg-ec-success and bg-ec-warn background tokens exist. There's no text-ec-success or text-ec-warn for inline text messaging. Currently uses ad-hoc text classes like text-ec-danger (which maps to a different color).
GAP 2 — No disabled-state tokens
Missing
No token for disabled text, disabled background, or disabled border. Components use ad-hoc opacity hacks (opacity-40, opacity-50) inconsistently. A proper --ec-disabled-text and --ec-disabled-bg would ensure consistent disabled states.
GAP 3 — No overlay/backdrop opacity tokens
Missing
The plan's A3 specifically calls for bg-ink/40 backdrop-blur-sm on the document viewer. But different modals use bg-ec-ink/40 (add-case-modal), bg-ink/30 (command palette), and bg-ec-ink/45 (doc-viewer-panel). No single --ec-overlay-opacity or --ec-backdrop token exists.
GAP 4 — Incomplete focus-ring token deployment
Inconsistent
Some components use focus-visible:ring-ec-honey, others use focus-visible:ring-ec-indigo (which shouldn't exist—indigo was killed in the design refresh). The global CSS has one focus ring: 2px solid var(--honey), but components override it inconsistently.
GAP 5 — No transition-duration tokens
Missing
The token file defines --motion-fast: 120ms and --motion-base: 150ms, but no Tailwind mapping exists. Components hardcode durations: duration-200, duration-150, duration-300.
GAP 6 — Legacy token bleeding
Debt
Settings pages still use legacy token names (border-line, text-ink-faint, bg-brand-50, btn-primary). The command palette uses bg-ink/30 and bg-surface. These should all migrate to ec-* equivalents.
3.3

Dark mode readiness

The token file has NO @media (prefers-color-scheme: dark) block defining dark values. The plan's own HTML has one but the actual app doesn't. The app relies on bg-ec-paper etc. which are defined in :root only (light).

Finding: The console has zero dark mode support. The mk-engraved masthead is already dark-ink-on-paper; the rest of the UI would invert poorly without explicit dark token definitions. This is a non-trivial undertaking and should be a tracked work order, not an incidental fix.
3.4

Typography consistency issues

ISSUE — Inconsistent label treatment
Bug
Three competing label patterns exist simultaneously: .ec-label (mono, small-caps, tracking), .eyebrow (same but with different spacing), and raw text-xs font-mono uppercase tracking-wider text-ec-ink-3 inline classes. Pick one and enforce it.
ISSUE — Stat number rendering
C1
The cases-attention.tsx renders stat numbers with .num class (mono). The prototype uses bold display serif. This is the C1 fix — but the deeper issue is that .num is mono-everywhere. A .stat class (bold Fraunces, tabular figures, larger size) should exist for this use case.
ISSUE — Devanagari tracking reset
OK
html[lang="hi"] resets letter-spacing on tracked labels. Good. But this only works when the lang attribute is set to hi — not when individual Hindi strings appear in English context (like the मुक़दमा wordmark).
04

Component architecture gaps

Shared primitives that exist, primitives that should exist but don't, and architectural debt.
4.1

The modal/dialog/drawer family — a mess

The app has three different modal implementations that don't share code:

ComponentMechanismFeaturesMissing
components/ui/dialog.tsx createPortal, Esc, overlay-click, scroll-lock, transition Shared, reusable, good. Focus trap, labelledBy enforcement, <dialog> element
add-case-modal.tsx Hand-rolled inline (no portal) Esc, overlay-click, scroll-lock Doesn't use the shared Dialog, duplicates scroll-lock logic, no backdrop-blur, no focus trap
case-detail-drawer.tsx Side-panel (no portal) Full-height slide-in No backdrop, no Esc handling, no scroll-lock
Recommendation: Before building A3 (document viewer backdrop), refactor add-case-modal.tsx to use the shared Dialog. Then fix the shared Dialog to support a variant="drawer" (slides in from right, used by filters drawer, case detail drawer, document viewer panel). One component, three variants: modal | drawer | sheet. This reduces future bugs to one surface.
4.2

No global toast system

The ONLY toast in the entire app is undo-toast.tsx — a single-purpose component for the bulk selection undo pattern. There is no shared success/error/info toast provider.

Where the app currently shows feedback:

  • Add-by-CNR success → inline green banner in the modal (A2 complains about this)
  • Profile save → inline feedback banner in the form
  • Client delete → inline ConfirmDelete with router.refresh
  • Stage change → UndoToast (only toasts that exist)
  • Case delete → no feedback beyond router navigation
  • Document actions → no feedback
Recommendation: Build a minimal ToastProvider + useToast() hook before any of the E-group work. The pattern: toast.success('Case deleted'), toast.error('Failed to sync'). Render at z-[100], fixed bottom-right, auto-dismiss 6s, stacked. This is ~80 lines. Every feature that mutates data (E1-E4) will need it.
4.3

Confirmation dialog — good foundation, missing variants

The ConfirmDelete and DeleteButton components follow a consistent two-step pattern. But they only cover deletion.

E3 needs "bulk delete with cascading consequences" warning. E4 needs "move to trash" confirm. F2's "..." menu has a Delete option with no confirmation at all (ref: case-actions.tsx line 128).

Recommendation: Extend the two-step pattern into a generic ConfirmAction component: title, description, confirmLabel, variant: 'danger' | 'warning' | 'default', children (for rich consequences like "This client has 12 linked cases"). Reuse for case delete, client delete, document delete, bulk delete.
4.4

Persistence strategy — three-way split

Three persistence mechanisms exist with no unifying strategy:

  • Cookie: Density toggle (DENSITY_COOKIE in cases-table.tsx)
  • URL params: Sort, filter, page, per-page, view (list/agenda), trash toggle
  • Server-side: Notification prefs, profile settings
  • E1 proposes: Cookie for column config
  • D4 proposes: "Per user" for sidebar width
Recommendation: Cookies are wrong for column config (4KB limit, sent on every HTTP request). Use localStorage for UI preferences (density, sidebar width, column config) with a usePersistedState hook that wraps useState + localStorage get/set. URL params remain correct for shareable filter/sort/page state. Server-side remains correct for auth-critical prefs.

06

Missing patterns & anti-patterns

Cross-cutting issues not covered by any plan item but visible in the codebase.
6.1

No date/time locale handling

Bug
"3/8/2026, 1:19:42 am" appears throughout the case detail page (US format). Indian lawyers expect "08/03/2026" (DD/MM/YYYY). The app uses next-intl — leverage it for date formatting. All court-record surfaces should use Intl.DateTimeFormat('en-IN') or the configured locale.
6.2

No "Undo" pattern beyond the bulk bar

Gap
The only undo pattern in the app is for bulk stage changes (10-second toast). Case deletion, client deletion, document move-to-trash — all permanent with no undo. Gmail-like "Undo" for destructive actions is table stakes for a lawyer dashboard where a wrong delete could mean losing a client's case data.
6.3

No optimistic UI updates

Gap
Every mutation in the app — add case, delete case, stage change, client delete, document action — waits for a full server round-trip before updating the UI. The user clicks "Delete" and sees nothing until the server responds. Even a 200ms Supabase latency feels slow. For mutations where failure is unlikely (delete, stage change), use optimistic updates: update local state immediately, roll back on error.
6.4

Inconsistent row hover/action patterns

Debt
  • Cases table: Row hover reveals action icons (Open, Cause list, Add note). Good.
  • Clients table: Row hover does nothing. No actions. The plan's E3 will fix this.
  • Documents list: Row hover reveals nothing. The trash icon sits statically in the row. E4 should add hover actions.
  • Inbox: Row hover highlights. Good. But no hover actions.
One pattern for all four tables: hover → reveal action cluster (View, Edit, Delete) on the right. Standardize.
6.5

No loading progress for long operations

Gap
The CNR lookup (add-case-form) can take 3-8 seconds as it scrapes the eCourts API. The submit button shows a pending state but no progress indicator. A skeleton inside the modal would be better than a frozen button. Similarly, the onboarding data fetch can take 10+ seconds for a first-time user — the polling lifecycle handles it, but the initial wait is a black box.
6.6

useEffect abuse for event wiring

Debt
The mk:new-case custom event pattern (A1) is fragile. It depends on the modal component being mounted, the event listener being registered, and no race conditions between the button click and React's render cycle. The correct Next.js pattern: router.push('/dashboard/cases?add=1') from the top bar, and the cases page reads searchParams.add to open the modal. URL-driven, not event-driven.
6.7

Z-index fragmentation

Debt
Z-index values across the app: z-[60] (doc viewer), z-50 (top bar), z-40 (mobile nav), z-[9999] (command palette — overkill). No z-index scale exists. If a toast system is added, where does it go? Define --z-sidebar: 10, --z-topbar: 20, --z-drawer: 30, --z-modal: 40, --z-toast: 50, --z-command: 60 as CSS variables in tokens.css.

Feature-specific design specs

Detailed UI/UX specifications for the four E-group features. What the plan says, what's actually needed, and how to build it.
7.1

E1 — Add-columns control

UX Design
Spec
  • Trigger: A + (plus) icon button at the right edge of the table header row, same height as the column header cells. Label: "Columns".
  • Popover: Opens on click. 260px wide. Contains a checkbox list. Available columns: Advocate, Stage, Case type, CNR, Synced, Diary date, Filing date, Court, Client. Default columns (always visible): Title, Next hearing, Status, Actions.
  • Reorder: Drag handles on each row. Drag to reorder column position.
  • Persistence: localStorage key: mukadma:cases:columns. Array of visible column keys + order.
  • Reset: "Reset to default" link at the bottom of the popover.
  • States: Loading (fetching prefs), empty (all checked = default), error (if localStorage parse fails → fallback to default).
Implementation

Accessibility audit

WCAG 2.1 AA baseline — keyboard, screen readers, color contrast, reduced motion.
A11Y-1 — No focus trap in modals
A
The shared Dialog component locks body scroll but does NOT trap focus. A keyboard user can Tab out of the modal into background content, getting lost. Fix: add a focus trap (either a tiny custom hook or use the <dialog> HTML element with showModal() which provides native focus trapping).
A11Y-2 — Icon-only buttons lack labels
A
The trash icon (E4), column picker icon (E1), collapse sidebar icon (D4), close buttons on modals/drawers — none have aria-label. Screen readers announce "button" with no context. Fix: every icon-only button needs aria-label="Delete document" or equivalent.
A11Y-3 — No skip-to-content link
A
No skip link for keyboard users to bypass the sidebar and top bar. Add: <a href="#main-content" class="sr-only focus:not-sr-only">Skip to content</a> as the first focusable element in the layout.
A11Y-4 — Color contrast on muted text
AA
text-ec-ink-3 (#8B8578 on #FAF9F7) has a contrast ratio of ~3.2:1 — below the 4.5:1 AA minimum for body text. This is used for "no activity", "no results", and secondary information throughout the app. Either darken the muted ink to at least #6B6558 or reserve it for decorative/large text only.
A11Y-5 — Reduced motion honored but incomplete
Polish
globals.css has a @media (prefers-reduced-motion: reduce) block that disables animations. Good. But JS-driven animations (slide-in drawers, document viewer entrance via useEffect) are NOT covered by this. Need to check matchMedia('(prefers-reduced-motion: reduce)') in JS to skip animation state transitions.
A11Y-6 — Table markup incomplete
AA
Cases table, Clients table, Documents list — none use <caption>, <thead>/<tbody> consistently, or scope="col"/scope="row". Screen readers navigate tables better with proper semantics.
A11Y-7 — Combobox ARIA incomplete
AA
The Combobox component doesn't implement the full ARIA 1.2 combobox pattern (aria-expanded, aria-activedescendant, role="listbox" on options). Fix as part of E2.

Performance considerations

Areas where the current plan's features could degrade perceived performance.
PERF-1 — Case detail page waterfall
Risk
The case detail page makes 15+ parallel queries on every request. Adding more sections (D1 reorder, D3 parties rework) doesn't increase the query count, but E-group features (E3 client bulk delete) will likely trigger a full page re-render. Use router.refresh() sparingly and consider revalidatePath for targeted cache invalidation.
PERF-2 — Documents page with 1000+ docs
Risk
The documents page currently uses server-side pagination. E4 adding filter + sort + bulk will increase query complexity. The bulk select for "all documents" is dangerous — selecting 500 documents and clicking "Download" would crash the browser. Add a cap (100 items per bulk action) and warn the user.
PERF-3 — localStorage for column config
Note
Using localStorage for column config is correct — it avoids the 4KB cookie limit and doesn't add request overhead. However, localStorage is synchronous and blocks the main thread on read. The usePersistedState hook should lazy-initialize with a default, then hydrate from localStorage in a useEffect to avoid blocking the first render.
PERF-4 — Sidebar resize during drag
Risk
A drag-to-resize sidebar fires pointermove events at 60fps+. Each event updates a CSS variable which triggers layout recalc. Use requestAnimationFrame throttling and set the width via style={{ width }} on the aside rather than a CSS variable to minimize recalc scope.
PERF-5 — No virtualization for large lists
Gap
The cases table could have 500+ rows for a busy lawyer. No virtualization (react-window or @tanstack/react-virtual) exists. Rendering 500 DOM rows is acceptable for now (Next.js server-side handles the initial render), but pagination with per=100 can still cause jank. Cap per at 50 and add virtualization if customers report slowness.

The Lovable → implement workflow

The current process — "Lovable prototype → implementer eyeballs it → code" — has already caused fidelity drift. The C1 stat numbers and C2 tab headings are the evidence: the prototype showed one thing, the code shipped another. A structured handoff prevents this.

Step 1
Lovable board → DESIGN.md annotation. For each design-first item, the founder creates the Lovable board and approves it. Then (this is the new step) a 5-line annotation is written into plan/design/DESIGN.md (or per-item plan/design/wo-XXX-design.md): 
## E1 — Column picker
Prototype: https://lovable.dev/project/xxx/board/yyy
Key rules:
- Popover: 260px, shadow-ec-3, right-aligned to header
- Drag handles on left of each checkbox row
- "Reset to default" link at bottom, text-ec-ink-3
- Persistence: localStorage, key: mukadma:cases:columns
- Default columns (always visible): Title, Next hearing, Status, Actions
- Available columns: Advocate, Stage, Case type, CNR, Synced, Diary date,...
This is the contract. The implementer implements against DESIGN.md, not from memory of the Lovable board.
Step 2
Taste tokens, not pixel values. Design annotations should specify tokens (shadow-ec-3, text-ec-ink-3, rounded-ec-m) not raw CSS (box-shadow: 0 8px 24px...). This keeps the implementation aligned with the design system and makes future token changes propagate automatically.
Step 3
Before/after screenshot in the PR. Every design-first PR includes a side-by-side: left = the Lovable reference, right = the built implementation. The reviewer (founder) approves fidelity by comparing the two. No screenshot = no merge. This closes the loop that caused C1 and C2 to drift.
Step 4
Lovable link in the WO file. When a work order says "implement the E3 client bulk actions," the WO file includes the Lovable board URL and the DESIGN.md path. The implementer opens both before writing a single line. No hunting for visual reference.
12.5

What NOT to do in Lovable

Anti-pattern: Using Lovable's "export to code" or "generate React" feature and pasting the output into the codebase. Lovable generates generic Tailwind classes and inline styles that don't use the ec-* token system. The result is a Frankenstein page where half the components use tokens and half use raw hex values. The Chambers prototype was used as a visual reference, not a code generator — keep that pattern.
Correct pattern: Lovable = visual spec. The implementer writes the code from scratch using the ec-* design system, with the Lovable board as the target to match. This ensures token consistency, accessibility, and the four-state pattern (loading/empty/error/success) that Lovable-generated code never handles.
